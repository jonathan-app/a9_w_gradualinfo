# MCP de engenharia

**Status**: Accepted
**Decision source**: aceite explícito do dono em 2026-10-10 à spec 0011 completa, incluindo este contrato filho, após revisão independente e correções autorizadas.

## Summary

A configuração MCP é específica do cliente; disponibilidade se comprova na sessão que fará a verificação.

## Requirements

- **mcp/AC-01**: cada configuração rastreada declara cliente, servidor, comando e versão exata sem segredo; a evidência registra a versão efetivamente iniciada.
- **mcp/AC-02**: `/check verify` dependente de MCP registra descoberta da ferramenta, chamada MCP real, URL local testada, status da resposta e captura com hash; invocar Playwright por CLI não satisfaz este AC. Sem essa prova, o AC afetado é UNVERIFIABLE.
- **mcp/AC-03**: Supabase MCP aceita apenas URL de loopback para a stack local, por exemplo `http://127.0.0.1:54321`; outro host falha na validação da configuração padrão.

## Decision

Tratar `.agents/mcp.json` como catálogo de intenção para agentes genéricos e `.vscode/mcp.json` como configuração do VS Code. Documentar explicitamente a diferença de servidores; não presumir que um arquivo ativa o outro. Manter `.agents/mcp_config.json` ignorado como configuração pessoal, sem usá-lo como fonte de verdade. Fixar versões exatas nos arquivos rastreados e registrar a versão iniciada em cada rodada. O primeiro cliente suportado para prova é o VS Code com o servidor Playwright MCP; a sessão descobre a ferramenta MCP, usa sua chamada de navegação para abrir `http://127.0.0.1:<porta>/api/health` e registra HTTP 200, corpo sem segredo e uma captura ou log com SHA-256. Se esse cliente não estiver disponível, a rodada fica UNVERIFIABLE. Outros clientes precisam do mesmo contrato antes de receber PASS.

## Standard definition

| Item              | Regra                                                                                                                     |
| ----------------- | ------------------------------------------------------------------------------------------------------------------------- |
| Canonical pattern | Catálogo genérico e adaptadores por cliente, com diferenças documentadas.                                                 |
| Enforcement       | Inventário local e smoke test na sessão de verificação.                                                                   |
| Falha             | Ferramenta ausente ou sem resposta gera UNVERIFIABLE nos ACs dependentes.                                                 |
| Rollout           | Documentar os dois arquivos rastreados, registrar versões e testar Playwright; ampliar aos demais servidores sob demanda. |
| Reversão          | Restaurar a configuração anterior do cliente; manter relatórios de indisponibilidade.                                     |

## Consequences

Um teste de ferramenta local não comprova comportamento da aplicação em produção. Servidores via `npx -y` podem resolver versões novas; a prova de revisão deve registrar a versão usada.

## Rationale

A separação por cliente corresponde aos arquivos já existentes. A prova de uso evita confundir configuração declarada com ferramenta funcional.
