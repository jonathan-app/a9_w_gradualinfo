## 4. Banco: ordem executada e como recuperar

A instrução era preservar o banco atual e registrar o acesso antes de mudar o
`project_id`. A sequência foi esta, e nada foi apagado em nenhuma etapa:

1. **Dump do banco atual** (`project_id = gradualinfo`), com o stack no ar:
   `~/Downloads/gradualinfo-db-dump-antes-de-gradualinfo-editorial-2026-10-05.sql`
   — 396.786 bytes, 10.033 linhas, PostgreSQL 17.11, SHA-256
   `dfdaf38d6886830445c53e13da23ed8da5c79ffa977d4cb791464287111d63eb`. É o banco
   inteiro, todos os schemas.
2. **`pnpm supabase:stop`** — sem `--no-backup`. Os containers foram removidos, os
   volumes preservados; a própria CLI confirma que os dados ficaram em volume.
3. Mudança do `project_id` e do `name`, depois `pnpm supabase:start`: novos
   containers e **novos volumes** `supabase_*_gradualinfo-editorial`.

Como acessar e restaurar cada banco:

```bash
# Abrir o banco atual, que está no volume antigo, já parado
podman start supabase_db_website_aqua9.com.br   # stack legada do AQUA9
podman exec -it supabase_db_website_aqua9.com.br psql -U postgres -d postgres

# Restaurar o dump do GradualInfo no stack novo
podman exec -i supabase_db_gradualinfo-editorial psql -U postgres -d postgres \
  < ~/Downloads/gradualinfo-db-dump-antes-de-gradualinfo-editorial-2026-10-05.sql
```

O dump usa `\restrict`, que é sintaxe de `psql` 17 ou superior — restaurar com
uma versão anterior falha. O dump da base legada ficou em
`~/Downloads/aqua9-website_db-dump-2026-10-05.sql` (34.856 bytes, SHA-256
`f8b5b5eadbfd89672bb15dfdfd2407320723cdf3ace16b63f198f7051eb49c4a`, schemas
`public` e `supabase_migrations`).
