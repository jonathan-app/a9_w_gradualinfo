# Auditoria profunda do a9_w_gradualinfo

Data: 2026-10-06

## Escopo

Auditoria estrutural e estática do ZIP atual do `a9_w_gradualinfo`, cruzada com:
- specs e estado persistente do projeto;
- código de aplicação;
- migrations e testes;
- Git/branches/worktrees;
- CI e scripts de gate;
- catálogo de skills;
- documentação oficial atual de Next.js, Supabase, MCP e OWASP.

A auditoria não trata histórico de execução como execução atual. Onde a evidência veio de relatórios anteriores, isso é indicado como evidência histórica.

## Estado geral

**Fundação de engenharia: AMARELA/VERDE**

**Prontidão para merge da feature atual: VERMELHA**

**Prontidão para produção: VERMELHA**

# 2. Findings P0

## P0-01 — Catálogo de skills não é reproduzível

### Evidência

O `skills-lock.json` fixa 9 skills:

- scope
- audit
- architect
- develop
- check
- test
- document
- sync
- debug

Porém a árvore `.agents/skills/` contém aproximadamente 101 `SKILL.md` no ZIP atual.

Ao mesmo tempo, `.agents/` está ignorado pelo Git.

### Risco

O projeto documenta "9 instaladas", mas o ambiente real contém muito mais capacidades não fixadas no lock.

Outro ambiente pode:
- não possuir as mesmas skills;
- possuir versões diferentes;
- carregar especialistas que não foram aprovados;
- produzir comportamento diferente do ambiente atual.

### Ação

Definir uma política explícita:

1. 9 skills core continuam canônicas.
2. Especialistas precisam entrar no lock antes de serem considerados disponíveis.
3. Se skills extras forem deliberadamente instaladas localmente, marcar como `local-only`.
4. Criar verificação automática:
   `installed skills == locked skills + allowlist local explícita`.

## P0-02 — `/check` existe, mas não é gate do `check:all`

### Evidência

`package.json` define:

`check:all = typecheck && lint && format:check && test:run`

Não chama:
- `check-decision.mjs`;
- `check-gate.mjs`.

O próprio `workflow/STATE.md` registra essa pendência.

### Risco

O repositório possui um mecanismo de aprovação formal, mas o comando principal de qualidade não o executa.

Logo:

`pnpm check:all verde`

não significa:

`entrega coberta por decisão aprovada`.

### Ação

Separar:

- checks mecânicos;
- decisão `/check verify`;
- revisão `/check review`;
- gate final ligado ao SHA.

O CI deve impedir merge quando o artefato de decisão estiver ausente, desatualizado ou reprovado.

---

## P0-03 — AC-06 é violado pelo código atual

### Evidência

A spec `md-0002` define AC-06 como:

> o corpo do artigo não usa `dangerouslySetInnerHTML` em nenhum caminho.

Porém:

`app/artigos/[slug]/page.tsx`

contém:

`dangerouslySetInnerHTML={{ __html: JSON.stringify(jsonLd) }}`

### Classificação

**FAIL estático do AC-06**, salvo se o AC for formalmente alterado pelo dono.

### Observação

O uso está no JSON-LD, não no corpo Markdown, mas o texto atual do AC é amplo: "em nenhum caminho".

Não devemos reinterpretar o AC depois da implementação.

### Ação

Escolher uma das duas decisões:

1. manter AC-06 amplo e substituir a injeção por um helper seguro de JSON-LD; ou
2. emendar o AC para permitir JSON-LD explicitamente, com requisito de escaping seguro de `<`, `>`, `&` e `</script>`.

A opção 1 é mais rigorosa.

---

## P0-04 — JSON-LD possui risco de quebra de `script` por conteúdo editorial

`JSON.stringify()` sozinho não neutraliza uma sequência `</script>` dentro de dados.

Como título, descrição e autor vêm do banco, conteúdo editorial malicioso pode atingir o bloco JSON-LD.

### Ação

Criar serializador seguro para JSON-LD que escape pelo menos:
- `<`
- `>`
- `&`

e principalmente sequências que possam terminar o elemento `script`.

Adicionar teste com payload contendo:

`</script><script>alert(1)</script>`

e verificar que o HTML servido continua com um único bloco JSON-LD válido e sem execução.

## P0-06 — `verify-result.json` está incompleto

- AC-01
- AC-02
- AC-03
- AC-04
- AC-12

todos como `UNVERIFIABLE`.

### Risco

Um artefato parcial não pode ser usado como decisão final de aprovação.

### Ação

- FAIL + evidência;
- UNVERIFIABLE + motivo;

# 3. Findings P1

## P1-01 — Segurança de headers ainda incompleta

`next.config.ts` possui:

- X-Content-Type-Options;
- Referrer-Policy;
- X-Frame-Options;
- Permissions-Policy.

Não possui:
- CSP;
- HSTS explícito.

Next.js documenta CSP e HSTS como controles disponíveis no mecanismo de headers.

### Ação

Criar threat model primeiro e depois aplicar:
- CSP compatível com Next/Sentry;
- HSTS somente quando HTTPS/canonical domain estiver definitivamente correto;
- `frame-ancestors` na CSP.

---

## P1-02 — ESLint perdeu regras específicas do Next

A configuração remove `eslint-config-next` para evitar uma cadeia de dependências problemática.

Isso reduz o conjunto de regras específicas do Next.

A documentação atual do Next.js recomenda `eslint-config-next/core-web-vitals` para projetos Next.

### Ação

Reavaliar o motivo do override contra a árvore de dependências atual.

Se a dependência problemática tiver solução atual:
- reinstalar o pacote oficial;
- usar Flat Config;
- ativar `core-web-vitals`.

Se não for possível:
- importar diretamente as regras necessárias do plugin;
- documentar a exceção.

---

## P1-03 — `<img>` é usado na página de artigo

A página usa:

`<img>`

em vez do componente de imagem do Next.

Isso pode prejudicar:
- otimização;
- dimensionamento;
- carregamento;
- LCP.

### Ação

Decidir entre `next/image` e uma estratégia explícita de imagem externa/R2.

Não mudar automaticamente: primeiro definir onde as imagens realmente serão hospedadas.

- title;

- canonical base.

## P1-05 — Sitemap ainda contém `/exemplo`

## P1-06 — Sitemap limita artigos a 1000 sem paginação

`getPublishedPosts(..., 1000)` coloca um teto arbitrário.

Para o MVP é aceitável, mas não escala.

### Ação

## P1-07 — Cache/revalidação editorial não está decidido

A spec reconhece que mudança de conteúdo exige revalidação, mas o serviço atual não estabelece uma política explícita de cache/revalidation.

### Ação

Escolher uma estratégia:
- conteúdo dinâmico;
- revalidate;
- cache tags;
- invalidation no processo de publicação.

Para o MVP, simplicidade vence.

---

## P1-08 — Preview usa token na query string

Endpoint:

`/api/preview?token=...`

O token pode aparecer em:
- histórico do navegador;
- logs;
- ferramentas de observabilidade;
- analytics/referer em cenários específicos.

### Ação

Preferir:
- POST;
- token de uso único;
- expiração;
- ou link assinado de curta duração.

Não usar senha fixa de conta de preview como mecanismo permanente.

---

## P1-09 — Comparação de token deve usar primitiva de tempo constante

O código implementa comparação manual byte a byte.

Funciona como tentativa de evitar comparação simples, mas a implementação merece ser substituída por primitiva criptográfica apropriada para o runtime suportado.

### Ação

Usar mecanismo equivalente a `timingSafeEqual`, com buffers de mesmo tamanho.

---

## P1-10 — Preview usa credencial compartilhada

O endpoint faz login como:

`preview@gradualinfo.dev`

usando `SUPABASE_PREVIEW_TOKEN` como senha.

### Risco

O mesmo segredo funciona como:
- token de acesso;
- senha do usuário.

Isso aumenta o raio de comprometimento.

### Ação

Separar:
- segredo do link;
- credencial interna;
- sessão curta;
- expiração.

---

## P1-11 — Acessibilidade ainda não está provada

O relatório atual marca AC-12 como `UNVERIFIABLE`.

Existe `@axe-core/playwright`, mas isso não é prova de execução.

## P1-12 — E2E não entra na CI atual

## P1-13 — E2E está fora do TypeScript check

### Ação

## P1-14 — Cobertura de testes está em 60%

O piso atual é:

- branches 60%;
- functions 60%;
- lines 60%;
- statements 60%.

Isso é aceitável para fundação, mas baixo para o caminho editorial que está prestes a publicar.

### Ação

Não aumentar para 80% artificialmente.

Subir por domínio:
1. serviços;
2. autorização;
3. parsing/renderização;
4. rotas críticas.

---

## P1-15 — Existem testes duplicados

Há pares em:

`__tests__/components/`

e:

`__tests__/unit/components/`

O mesmo padrão ocorre para `button`, `format` e `cn`.

### Ação

Eliminar duplicação ou documentar por que ambas as camadas existem.
